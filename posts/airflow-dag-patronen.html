Airflow-productie-DAG: patronen en valkuilen

[Kennis] 3 aug 2026 · 12 min · airflow data-engineering tooling

Een DAG is een contract met de toekomst: jij schrijft hem nu, iemand anders — mogelijk jij over twee jaar — moet hem begrijpen wanneer hij om 03:00 faalt. Deze patronen zijn wat dat verschil klein houdt.

1. Orchestratie in de DAG, logica in een module

De DAG beschrijft wát er wanneer draait; hoe een taak transformeert hoort in importeerbare code, testbaar zonder Airflow.

from airflow.decorators import dag, task
from datetime import datetime

import greenhouse_transforms as gt  # puur, testbaar zonder Airflow

@dag(start_date=datetime(2026, 1, 1), schedule="0 4 * * *",
     catchup=False, tags=["sensoren"])
def sensor_aggregatie():
    @task
    def laad():
        return gt.laad_ruwe_registraties()

    @task
    def aggregeer(regels):
        return gt.aggregeer_dagelijkse_reeks(regels)

    aggregeer(laad())

sensor_aggregatie()

De module greenhouse_transforms is met gewone unit tests te dekken; de DAG zelf blijft dun en bevat geen zakelijke logica.

2. Idempotentie boven alles

Elke task moet opnieuw kunnen draaien zonder schade. Concreet:

  • Schrijf naar een tijdelijke tabel of bestand en swap hernoem je resultaat atomisch.
  • Gebruik INSERT ... ON CONFLICT DO UPDATE in plaats van blind INSERT.
  • Noem bestanden met de logical date, niet met de wall-clock time: een herstart van dezelfde run overschrijft zichzelf.
INSERT INTO greenhouse.daily_agg (day, sensor_id, avg_c)
VALUES (:day, :sensor_id, :avg_c)
ON CONFLICT (day, sensor_id) DO UPDATE SET avg_c = EXCLUDED.avg_c;

3. Retry-beleid is een domeinbeslissing

De default (retries=0) negeert de realiteit: netwerken haperen. Maar oneindig herhalen maskeert defecten. Mijn basislijn:

default_args = {
    "retries": 3,
    "retry_delay": timedelta(minutes=5),
    "retry_exponential_backoff": True,
    "execution_timeout": timedelta(hours=2),
}

Twee vallen daarbuiten: een taak die op een external API faalt met 4xx hoort niet te retry'en (keuze in de code), en een taak die nooit meer dan enkele seconden duurt heeft een execution_timeout nodig die dat afdwingt.

4. Traps

  • catchup=True vergeten — bij een start_date in het verleden start Airflow een backfill die niemand wilde.
  • Groeiende rendered-velden — templating op grote payloads maakt de metadata-database traag; geef grote waarden door via XCom met een externe backend ofsla ze als bestand.
  • Dependencies via >> in plaats van expliciete argumenten — leesbaarheid verdwijnt zodra een DAG meer dan een handvol taken heeft.
  • Secrets in code — Airflow heeft een secrets-backend; gebruik Variable.get of connections, nooit literals.

Controlelijst vóór productie

  1. Draait een herhaling van dezelfde run zonder duplicate rows?
  2. Is elke task voorzien van een realistische timeout?
  3. Is catchup expliciet gezet?
  4. Bevat de DAG geen logica die ook zonder Airflow zou moeten bestaan?
  5. Geven de logs bij een fout de werkelijke oorzaak, of alleen "task failed"?

Checken kan lokaal met airflow dags test voor een enkele run zonder scheduler — goedkoper dan het in productie ontdekken.
