Waarom deze kennisbank platte HTML is

[Blog] 1 okt 2026 · 4 min · tooling web

Ik heb de afweging Jekyll tegenover platte HTML gemaakt zoals ik elke afweging maak: wat gaat er kapot als ik de complexste optie kies? Bij een site met enkele tientallen pagina's is het antwoord: niet veel, maar ook niet veel dat ik terugkrijg.

Wat de Jekyll-route had opgeleverd

_posts met front-matter, een collectie voor kennisartikelen, een search.json die GitHub Pages zelf bouwt. Prima — maar GitHub Pages bouwt met een vaste Ruby-versie, een vaste set plugins en een build die ik niet lokaal reproduceer zonder bundle install. Elk probleem met die pipeline los ik op afstand op.

Wat platte HTML oplevert

  • Geen build-fase: wat in de repo staat, staat in productie.
  • Lokaal openen werkt — index.html dubbelklikken en de site doet het, inclusief zoeken.
  • De zoekindex is een JS-bestand dat als script geladen wordt: geen fetch, dus ook geen CORS- of netwerkgedoe. Zoeken is een array-filter, direct.
  • Eén bron van waarheid (content/index.js) betekent dat het overzicht en de index niet uit elkaar kunnen lopen — zolang je de stappen volgt bij het toevoegen van content.

De kosten

Twee, eerlijk gemeld. Ten eerste is er geen redactie-flow: nieuwe content betekent een HTML-pagina kopiëren en een regel toevoegen aan de index. Dat is twee minuten werk en geen formulier. Ten tweede: zonder JS geen lijst. Voor een persoonlijke naslag accepteer ik dat; zou dit een site voor derden zijn, zou ik server-side rendering willen.

# lokaal bekijken zonder server
start index.html

# of via een simpele static server
python -m http.server 8000

Wanneer ik het zou herzien

Bij meer dan ~200 items wordt het handmatige indexwerk vervelend, en bij echte redacteuren al veel eerder. De afstappunt is dan een generator die uit markdown de HTML en de index schrijft — nog steeds statische output, maar niet meer handmatig. Zolang dat niet het geval is, blijft het bij wat het is: bestanden, een browser, geen bouwlaag ertussen.
